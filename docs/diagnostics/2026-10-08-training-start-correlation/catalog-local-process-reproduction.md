# Local DB221 process-accounting reproduction

## Purpose and scope

This is a bounded local reproduction of `get_available_word_lists(uuid,text,text)` as installed by DB221. It compares the actual migrated implementation with an isolated function clone whose body fingerprint is required to match, with and without the proposed covering index on `(word_entries.id) INCLUDE (dictionary_id)`. The measurements help characterize backend process cost under controlled local conditions; they do not estimate production CPU attribution or justify a production index/migration by themselves.

The fixture uses the real 18,163-entry Van Dale source corpus and the exact production `vandale-all`/`nt2-2000` memberships. Input-key, content-fingerprint, and membership verification is documented in [catalog-real-corpus-verification.md](catalog-real-corpus-verification.md). One approved #341 correction is replayed only in the disposable database, guarded by the exact source key and prior fingerprint. An additional 61-row synthetic QA/access fixture represents secondary dictionary states without copying private dictionary content or learner data. The report must distinguish the real source corpus from these marked synthetic rows.

The test provisions a fresh native Supabase PostgreSQL 17.6.1.106 container for each resource profile, binds only a dynamically selected loopback port, uses no volume, and removes its own container in `finally`. Port 54322 and the canonical local database are excluded. The native image supplies its Auth schema and `auth.uid()` function, but the full Supabase Auth/GoTrue, PostgREST, and pooler services are not part of this direct-RPC experiment. Bootstrap runs in the disposable cluster only; setup-specific extension creation/ownership steps are not production migration changes.

## Measurement protocol

The bounded matrix is two resource profiles × two index states × three fresh backend pairs per index state. The baseline container is capped at 4 CPUs and 8 GiB memory; the constrained profile is capped at 0.5 CPU and 512 MiB memory with swap disabled. CPU and memory are therefore changed together in the constrained profile, so that arm is a combined resource-stress comparison, not an isolated CPU-only test. PostgreSQL settings match the captured production planner settings where applicable; `max_parallel_workers_per_gather=0` makes leader-process accounting interpretable but differs from production's value of 1.

Each pair uses one persistent direct `psql` connection and the same backend PID for two authenticated RPC calls. Backend PID and container PID namespace are checked against the disposable cluster identity. Transaction setup, role/claim, and effective settings are prepared before the process-counter baseline. `/proc/<pid>/stat` is sampled around each `DO` invocation, and the RPC separately records its own server-side wall interval and response hash. User/system CPU, minor/major faults, and resident bytes are derived from process counters; the container cgroup snapshots are contextual aggregate evidence, not backend-attributed CPU. Nested `EXPLAIN`/`auto_explain` plans are captured outside the timed calls, after a state’s timed pair.

Calls are fresh-backend calls, not cold-cache calls. Import, parity validation, and earlier calls warm database/OS cache; the imported fixture is intended to fit within the configured shared buffers. The index order alternates AB/BA across pairs, but plan capture and prior state execution can still perturb cache state. The process interval is an approximation of CPU spent in the `DO`: it includes RPC response hashing and GUC bookkeeping after the server-side wall timer stops. The `/proc` tick resolution is 10 ms, which is coarse relative to short repeat calls. Cgroup deltas also include the sampler's own `docker exec`/shell activity. These limits preclude a precise per-RPC CPU ratio.

Before accepting timings, the run records the actual DB221 function body fingerprint, source-import and membership guards, 30 authenticated JSON-parity cases across null/normalized/unexpected language and curated/user/unexpected type inputs, relation width/count/size statistics, nested plan shape, and per-call response hashes. Timing summaries must report first and repeat calls separately and retain all observations; do not describe a result as a tail-latency measurement.

## Results

Both profiles completed all six fresh-backend pairs per profile (three per index state), with two calls per backend. Timed calls invoked the isolated clone; its `prosrc` fingerprint was required to equal the actual migrated DB221 function, and the actual RPC and clone passed the preceding JSON parity checks. Server-side RPC wall-time medians across the three backends were:

| Resource cap | Index state | First call | Repeat call |
| --- | --- | ---: | ---: |
| 4 CPU / 8 GiB | Covering index present | 15.406 ms (15.006–16.743) | 12.918 ms (11.850–12.997) |
| 4 CPU / 8 GiB | Covering index absent | 20.045 ms (19.839–20.757) | 15.701 ms (15.699–16.556) |
| 0.5 CPU / 512 MiB | Covering index present | 13.891 ms (13.803–14.132) | 9.587 ms (9.482–10.591) |
| 0.5 CPU / 512 MiB | Covering index absent | 17.071 ms (16.340–17.110) | 13.166 ms (12.729–13.821) |

In both warm, serial local profiles, the indexed arm was faster in all three pairs for both call positions. The constrained arm happened to be faster than the baseline arm; it must not be read as evidence that fewer resources improve query latency. Per-call cgroup deltas showed no CPU throttling during either profile’s measured DO windows. The constrained container accumulated about 12.1 seconds of throttling during setup/import before timing, and its memory peak reached the 512 MiB cap with `memory.events:max` incrementing during setup; there were no OOM events and no corresponding measured-call deltas. This illustrates why a cumulative cgroup total cannot be assigned to the RPCs.

Process user CPU was reported in 10 ms ticks (mostly 10 or 20 ms per DO bracket), too coarse to support fine comparisons against ~9–21 ms RPC wall time. Across all 24 calls, major faults were zero; minor faults ranged from 1,695 to 2,352 on first calls and 662 to 678 on repeats. Minor faults reflect process page mappings/population and are not a direct disk-I/O counter. In both profiles, indexed backends’ RSS after calls was about 38–40 MB; no-index was about 76–78 MB. These are observed process counters, not an attribution of the RSS difference to a specific plan node.

The nested plans show the expected access-path change: with the covering index, `entry_sources` uses an `Index Only Scan` on `catalog_fixture_entry_identity_source`; without it, the same CTE uses a `Seq Scan` of all 18,224 `word_entries`. In the baseline profile, the indexed source scan touched 113 shared blocks and reported four heap fetches; the no-index scan touched all 4,310 heap pages. The whole nested plan reported 21,621 versus 25,818 shared hits in the first pair; reads were zero because buffers were warm. This supports reduced buffer work for this specific shape, but the physical fixture has about half the production heap size, and the index's visibility-map behavior/working set is not production-equivalent.

Both profile runs verified the same migrated-function source fingerprint (`d2130ec2041ae2f22b004903cc413e635c5e8c12df0d847f7383fe9cd142ce67`) and recorded 30 authenticated JSON parity cases before timing. Within each profile, every timed response had the same result hash across both index arms and all six backends. The saved matrix has 24 calls total; all had zero major faults, with per-call cgroup `throttled_usec` delta zero. The complete ignored summary is `tmp/latency-audit/catalog-db221-process-repro/summary.json` (SHA-256 `6ef043f80442bd9eda225e355dbc49490593d9708fbb173331f1c3167a23be58`); it also preserves per-call process counters, server timestamps, effective settings and cgroup snapshots. The profile-specific nested plans are saved alongside it in the same ignored evidence directory. Both owned disposable containers were removed; the canonical local service remained untouched.

These measurements establish a plausible local benefit from avoiding the heap scan, but not production impact. The test used direct local backends, serial execution and a warm cache, not production pooler scheduling or concurrent load. If a further experiment is justified, reproducing the production heap/visibility/history shape on a disposable database is more informative than repeating this same compact fixture on a different host. No production DDL is warranted from this result alone.

The imported fixture has 18,224 rows, including the 18,163 real Van Dale rows and 61 marked synthetic secondary/QA rows. The real source keys and corrected content fingerprints, plus both production collection memberships, passed their guards. The QA secondary content is synthetic. The fixture heap was 35,307,520 bytes over 4,310 pages, versus the production aggregate’s 71,475,200 bytes over 8,725 pages. Average row size was close (1,753 vs 1,760 bytes), but the heap is about half the production size. The disposable import is freshly compacted and does not reproduce production’s physical history, dead space, or bloat; do not read this benchmark as a physical clone. The 61 small QA rows fall in the 0–511-byte width bucket; other width bucket differences remain part of the known approximate shape match.

The experiment has not run on the NUC.

## NUC feasibility

A later NUC subset is technically feasible without installing host PostgreSQL tools: the NUC has Python 3 and Docker, and the disposable database can be driven with `docker exec ... psql` from a standalone runner. The host has 4 logical CPUs and 16.7 GB total memory, with about 12,773 MiB available and roughly 25 other Docker services. Any NUC execution must retain the dedicated 0.5-CPU/512-MiB/no-swap container cap and avoid resource-heavy unrestricted arms. This feasibility assessment is not a measurement: the disposable native image, schema/corpus transfer, port isolation, and cleanup must be independently checked there before interpreting a NUC result. A NUC subset would test portability and weaker-host sensitivity, not replace the paired local matrix or establish production backend CPU cost.

## Reproduction artifacts and privacy

The runner and generated evidence live under ignored `tmp/latency-audit/catalog-db221-process-repro/`; source corpus and exact membership map remain ignored inputs. These artifacts include local dictionary payloads and should not be committed or attached to broad logs. No learner histories, account data, production raw content export, canonical database writes, or production DDL belong in this experiment.
