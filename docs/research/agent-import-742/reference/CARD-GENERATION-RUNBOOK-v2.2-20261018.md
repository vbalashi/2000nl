# Генерация и редактура словарной статьи: проверенный регламент

Версия 2.2 · обновление 18 октября 2026 · исследовательский процесс, не контракт импорта.

[Сохранённая версия 1.0](CARD-GENERATION-RUNBOOK-v1.0-20261017.md). Новые небольшие запуски используют [обвязку v2](scripts/card_pipeline_v2/README.md). Исторические run-local scripts и их pinned snapshots сохраняются для воспроизведения.

Этот документ предназначен агенту, которому передают одно слово, выражение или список из 1–10 кандидатов. Он объединяет фактический процесс генерации, проверки и последующей редактуры. Обвязка v2 переиспользует core runtime, принимает явные packets/manifests, проводит semantic proposal/critic, сохраняет Root acceptance и собирает отдельную research-партию. Проверки владельцев/регистрации и содержательная приёмка остаются задачей агента; строка слова сама по себе не является готовым входным packet. Это набор контролируемых команд, а не автономный API словаря.

Для планирования новых300–900 начать с [короткого launch brief](START-NEXT-BATCH.md) и [cohort quality gate](BATCH-QUALITY-GATE.md). Это предложенный контракт запуска; общего cohort coordinator эти документы не объявляют реализованным.

## 1. Что должно получиться

Результат — новая исследовательская версия статьи с нидерландскими определениями, примерами, необходимой грамматикой, классификацией существующих выражений и проверяемой историей. Это ещё не полная карточка приложения, не перевод и не импорт в БД.

У статьи три уровня:

- **Кандидат:** постоянный `candidate_id`, исходная лемма реестра, сведения о выборе и корпусных частотах. Частота написания не равна частоте каждого значения.
- **Лексическая единица:** слово определённой части речи/омограф либо целое выражение. У неё собственный `unit_id`, грамматика и значения.
- **Значение:** `sense_id`, оригинальное `definition_nl`, примеры, ограничения употребления. После редакторской проекции примеры получают `example_id`.

В первом проходе каждое значение получает ровно два различных примера. После объединения близких значений примеров может стать больше: редактор обязан сохранить исходные примеры. У выражения собственные значения; ссылка `display_parents` лишь предлагает, под каким словарным значением его показывать, и не переносит туда его смысл.

Регистр/тематика, парадигмы форм, синонимы/антонимы, переводы, IPA/аудио и учебная сортировка не должны незаметно включаться в этот проход. Существенная для смысла грамматика и необходимые выражения, напротив, входят сразу. Имена, организации и географические названия допустимы; их нельзя автоматически исключать только за статус собственного имени.

**Условие окончания небольшой задачи:** у каждого переданного кандидата есть либо принятая версия ядра и результат последующей редактуры, либо конкретное проверенное решение о существующем владельце/навигации, либо сохранённый нерешённый вопрос с последней пригодной версией и следующим действием. Последний случай не называется готовой статьёй. «Обработано 10 кандидатов» не обязательно означает «готово 10 новых статей».

## 3. Полная последовательность

| Шаг | Вход → выход | Исполнитель | Новые API-вызовы |
|---|---|---|---|
| 0. Идентичность/владельцы | Лемма и список → проверенные candidate IDs, исходные владельцы/сомнения | Код + агент | Обычно нет; поиск источников по необходимости |
| 1. Подготовка | Кандидаты, контексты, scope → immutable inputs, журнал начальных замечаний, версии и preflight | Код + агент | Нет |
| 2. Генерация | Один кандидат и контексты → полная статья с локальными ключами | Luna high | Один логический запрос на кандидата |
| 3. Независимая критика ядра | Полная статья, before/diff/lineage и журнал → семь проверок, issues и явное closure | Sol low | Один логический запрос |
| 4. Ограниченные исправления | Статья и замечания → полная исправленная статья, lineage, повторный критик | Luna high → Sol low | До двух дополнительных циклов |
| 5. Приёмка ядра | Вся последняя статья, критика, история, источники → hash-bound решение | Root/назначенный редактор | Отдельный Azure-вызов не обязателен; работа агента не бесплатна |
| 6. Смысловая редактура | Принятое ядро + релевантные связи → полная обновлённая статья и change_log | Sol high | Один логический запрос |
| 7. Независимая проверка редактуры | Вход и предложение, изменения и контекст → вердикт и замечания | Sol high, отдельный вызов | Один; до двух циклов доработки предложения |
| 8. Итоговое решение/согласование | Все результаты → окончательные решения, адресный аудит выражений/владельцев | Root + код | Нет обязательного повторного массового API коллекции |
| 9. Сборка | Принятые результаты + база → новая исследовательская версия/manifest/отчёт | Код + агент | Нет |

«Независимый» здесь означает отдельный вызов с ролью критика, а не другую модель обязательно. Два последних шага используют одну модель Sol high с различными ролями. Это не заменяет внешнего лингвиста и не доказывает безошибочность.

### 3.1 Подготовка кандидата и контекстов

1. Найти точный `candidate_id` и написание в реестре; проверить текущие принятые статьи, ранее начатые попытки и навигации. Не создавать новый UUID для уже существующего кандидата. Если слова вообще нет в реестре, нужна отдельная явная регистрация кандидата с происхождением и стабильной identity; текущий batch runner проверяет исходный реестр и не поддерживает такое добавление просто подменой входного UUID. В этой документационной работе реестр не расширяется.
2. Установить, что нужно: новое ядро, исправление уже существующей статьи, вариант/форма существующего владельца, собственное имя или неясная идентичность. Совпадение строки само по себе не даёт решения.
3. Для новых входов использовать [подготовку через поиск v2](scripts/local_search_v2/PREPARATION.md): hybrid surface/lemma, исправленная идентичность источника, отдельный полный архив и подборка в prompt. Кандидатов и reservation по-прежнему готовит upstream coordinator. Исторический retrieval использует до шести дедуплицированных **письменных train** фрагментов точного написания; он может пропустить склонённые формы, раздельное написание глагола и устную речь. Нельзя объявлять такую выборку полным перечнем значений.
4. Корпусный фрагмент хранится со ссылкой/record ID, хешем, offsets и проверяемым target span. Фрагменты — исследовательское свидетельство, а не текст для перепубликации примера.
5. Неясное имя/аббревиатуру/слово проверять по положительным источникам. Недоступность сайта не доказывает отсутствие слова. Не приписывать имя конкретному человеку по одному совпадению написания.
6. Сохранить исходный пустой `unresolved` seed и required `source:initial_generation`, scope, версии исходников/схем/промптов, точные собранные сообщения, разрешённые модели и лимиты. API — только после успешного preflight.

Исторический выбор следующей партии: сумма `1/sqrt(corpus_rank)` по спискам, с дополнительными правилами ties и исключением начатых кандидатов. Для пользовательских 1–10 слов частотный селектор не нужен: состав задаётся явно, но идентичность и предыдущую работу всё равно проверяют.

### 3.2 Что генерируется и проверяется

Генератор возвращает JSON статьи, а не свободный текст и не окончательный глобальный каталог. Поля ядра: `candidate_id`, `lemma`, `route`, `scope_rationale`, `coverage_issues`, `units`. У unit — локальный `unit_key`, kind, lemma, POS, article/gender, essential grammar, pattern/components и senses. У sense — `sense_key`, definition, два примера и usage constraints. UUID назначает вызывающий код.

Четыре фактических маршрута модели:

- `word_senses`: есть самостоятельная word-unit; необходимые выражения могут сосуществовать.
- `construction_based`: существенный смысл требует конструкции; это не автоматическая идиома.
- `expression_only_in_scope`: нет выдуманного свободного значения компонента, есть собственные expression-units.
- `unresolved`: идентичность или существенное покрытие не установлено. Это блокер принятия ядра.

В текущей core schema нет отдельного POS `proper_noun`, а noun-word schema требует article/gender: новые собственные имена требуют явного совместимого representation/recovery решения, а не обхода валидатора. Для некоторых собственных имён принималась явная representation через `other` и `not_applicable`, с обоснованной грамматикой. Это техническое представление не означает, что у имён вообще нет артикля/рода. Не добавлять выдуманный enum и не переносить это исключение на обычные существительные.

Семь проверок критика: identity/POS, noun article/gender, sense coverage, definition accuracy, examples, expression boundary, provenance/scope. `needs_review` должен сопровождаться структурированным замечанием. В closure-режиме каждому предыдущему issue требуется явное `open`/`closed` с доказательством. Исчезновение замечания из следующего ответа не является его закрытием.

JSON/schema/семантический валидатор проверяет допустимые поля, ключи, часть ограничений, пары примеров и маршруты. Он не доказывает лингвистическую истинность определения. `duplicate_examples` ищет конкретное совпадение с контекстами; это не универсальная проверка оригинальности.

### 3.3 Исправления и эскалация

Основной автоматический цикл: generate → critic → при необходимости revise → critic → ещё revise → critic. Это максимум **три предложения статьи и три проверки**, до физических повторов в общем transport/format/validation пуле. Исправитель возвращает статью целиком вместе с lineage/решениями, а не только список оценок. Корректные посторонние поля сохраняются.

Если остались обязательная ошибка, неясная идентичность, недоказанная смена владельца или неправильная lineage, задача выходит из обычного автомата. Агент читает всю конечную статью, а не только текст последнего замечания. Возможны точная ручная правка, сбор источников, отдельная направленная проверка и честное отложенное решение. Бесконечный автоматический repair-loop не предусмотрен.

Содержательная правка определения/грамматики не становится проверенной из-за старой критики прежнего текста. При отдельной независимой перепроверке сохраняют точные новую статью, delta и свежую рецензию. Некоторые исследовательские грамматические правки принимались непосредственно Root с явной пометкой, что прежний критик исторический: это другой метод приёмки, не имитация свежего API-review. Для нового маленького запуска рекомендуемый единый порядок — содержательная правка → свежий core critic → Root. Это рекомендация стандартизации, а не заявление, что вся история уже следовала ей.

### 3.4 Редакторский проход после ядра

Адаптер [adapter_v2.py](experiments/next1200-batches21-24-v1/editorial/adapter_v2.py) требует принятую Root статью с точными article/history pins. Он не принимает `model_ready` вместо требуемого решения и не разрешает незаметно редактировать старую базу. Важно: `project` проверяет поля reviewer/decision и exact pins, но сам по себе не доказывает факт содержательного чтения и не проверяет все признаки unsigned draft/`Root_signed`. Настоящую приёмку обязаны подтвердить подготовка/authority и итоговый receipt audit; JSON с похожими полями не заменяет решение редактора.

Редактор получает полную статью, допустимые merge IDs, релевантный cross-entry context и обязательный контекст: history pin, critical ledger, Root changes, source obligations, выбранные corpus contexts. Полная история остаётся доступна вне запроса; нельзя просто убрать из компактного запроса содержательные обязательства под видом экономии.

Разрешены:

- объединение близких значений **внутри одной unit** с проверяемой историей;
- метаданные существующих выражений: `idiom`, `fixed_collocation`, `productive_construction`, `uncertain`;
- локальные display-parent ссылки на реальные unit/sense IDs.

При разрешённом merge создаётся обобщённое определение объединённого значения и новый разрешённый sense ID; старые определения сохраняются в change_log. Не разрешены этим редакторским контрактом: добавление самостоятельных новых значений, произвольное переписывание определений вне merge, новые примеры/части речи, изменение грамматики, удаление неудобных значений, перенос между разными unit без отдельного маршрута. Найденный такой дефект становится `concern` и отдельной задачей core-исправления. Нельзя заставить grouping critic удостоверить новую фактическую дефиницию.

Редактор возвращает **полную обновлённую статью + change_log + concerns**, затем независимый критик проверяет предложение. Технический валидатор проверяет ID, сохранение примеров/грамматики/ограничений, допустимые операции и ссылки. Root читает фактические изменения, сомнения и итоговый результат, после чего отдельно принимает его.

Если объединений нет, результат всё равно полезен: статья может получить метки выражений или подтверждённое отсутствие допустимых изменений. `uncertain` — честное состояние, а не ошибочный ответ по определению. Например, смешанное буквальное/идиоматическое выражение или имя организации может не помещаться в три уверенные категории.

## 4. Когда нужен routing и участие Root

Под routing здесь понимается выбор ветки обработки, а не автоматическая смена дешёвой модели на дорогую. **Доказанного общего семантического классификатора «этот случай требует Sol high, а этот нет» нет.** Роли закреплены политикой; адресное решение принимает агент. Если под «рутингом» имеется в виду участие Root, в действующей схеме оно есть при обеих приёмках, а углублённый разбор требуется в строках ниже.

| Ситуация | Маршрут | Что нельзя делать |
|---|---|---|
| Обычное новое слово/выражение, ясный владелец | Обычный core-loop → Root → grouping-loop → Root | Принимать только по `model_ready` |
| Есть only optional замечания | Root оценивает обязательность; сохраняет их явно | Объявлять все optional исправленными или делать их бесконечным барьером |
| Неправильный JSON/refs/closure | Ограниченный форматный retry с сохранением ответа; при исчерпании — разбор | Ослаблять schema ради зелёного результата |
| Network/timeout/429/5xx | Проверить журнал и in-flight; bounded transport retry/backoff | Запускать второй процесс или генерацию заново, если готово предложение/критик |
| Usage пропал | Записать unknown, продолжать по текущей политике, учитывать известные расходы отдельно | Придумывать нулевую цену или останавливать только из-за unknown |
| Content filter / provider refusal | Зафиксировать точный статус/категорию, локальное ожидание и решение | Считать это rate limit или слепо повторять тот же отклонённый запрос |
| Форма/вариант существующего слова | Сопоставить полную статью и конкретные owner senses; собственное значение может остаться | Делать глобальный alias по похожему написанию |
| Собственное имя/аббревиатура | Проверить источник и границы; применить подходящую POS/грамматическую модель | Отбрасывать все имена или выдавать часть названия за отдельную лемму |
| Неясное слово/недостаточно источников | Положительный поиск, ограниченная recovery-задача или explicit hold | Выдумывать значение; трактовать отсутствие найденного источника как доказательство отсутствия слова |
| Core-дефект найден на grouping | Отдельная exact core-repair, при необходимости свежий core critic; затем новый grouping по новой версии | Принять старую проверку как относящуюся к новому тексту |
| Общая идиома в нескольких статьях | Адресно сравнить определения/примеры/классы/owner; сохранить историю | Автоматически слить по одной строке lemma/pattern |
| Смена units, split/reparent/retirement | Проверяемый lineage и зависимые ссылки, точное Root решение | Переиспользовать старый ID для нового смысла или удалить источник без истории |

Owner-route фиксируется отдельным sidecar: source scope, точный pin owner-статьи, target unit/sense IDs, непустое условие каждого binding, явное решение Root и ambiguity policy. Неоднозначность не превращают в `global_alias=true`; существующая статья может сохранить собственный непокрытый owner смысл.

Три реальные иллюстрации:

- `boren`: новая содержательная дефиниция проверялась отдельным fresh **core** critic, а не grouping critic. [Контроллер](experiments/next1200-batches21-24-v1/editorial/boren_core_critic_controller_v1.py).
- `lam`: grammar уточняет `lamleggen` против `lam te leggen`; контекст имени Lam Bao этим не разрешается. Принятие общего ядра и незакрытая грань имени могут сосуществовать. [Пакет полного чтения](experiments/next1200-batches21-24-v1/bounded-repair-cohorts21-22-preparation001/root-authorized14-materialization001/149aa364-8030-5698-a63f-642479e7c278-Root-full-reading001.json).
- `ho maar` и `Media Lens`: `uncertain` сохраняет соответственно смешанную семантику и ограничение таксономии собственных имён. [Три сохранённых замечания](experiments/next1200-batches21-24-v1/editorial/independent-output-audit40001/all-three-concerns001.json).

## 5. Версии, модели и что на самом деле отправляется

| Роль | Deployment в наблюдаемой политике | Effort | Cap output, включая reasoning |
|---|---|---|---:|
| Генерация и core-revise | `gpt-6-luna` | high | 24 000 |
| Независимый core critic | `gpt-6.1-sol` | low | 12 000 |
| Semantic proposer | `gpt-6.1-sol` | high | 12 000 |
| Независимый semantic critic | `gpt-6.1-sol` | high | 12 000 |

Это закреплённая конфигурация данного исследовательского процесса, не гарантия существования таких deployment в любом Azure-аккаунте. Публичный тариф по этим именам здесь не заявляется. Старые версии использовали другие режимы.

**Ловушка чтения исходников:** алгоритм `stage01_batch08` содержит low/12k/6k аргументы. Реальный `EffortCaller` переопределяет effort и cap по роли, а `Batch20Caller` повторно проверяет фактический request body. Поэтому режим определяют по цепочке controller → wrapper → фактический JSON, а не по одной строке алгоритма.

Основная генерация читает `prompts/generate.txt` **плюс batch editorial appendix**, а schema добавляется в собранное сообщение. Основной core critic/repair используют `editorial_revision.messages('review'/'revise')`, то есть `editorial-review.txt`/`editorial-revise.txt`, closure/revision schemas и конкретный body. Отдельный Boren critic использует `review.txt` и простой review schema. Это разные формы запроса; нельзя назвать один `review.txt` всем действующим критиком.

Grouping использует byte-pinned `editorial/reuse-v39/proposer-global-v1.txt`, `critic-global-v1.txt` и `schema.py`. Повторное использование этих трёх компонентов не означает запуск старого v39 runner с его собственными лимитами и составом.

Для воспроизведения закрепляют не только файл промпта, но и его appendix, schema, message builder, исходную статью/контекст, wrapper, deployment/effort/cap, assembled messages и хеш запроса. Не менять замороженный prompt «на месте»; новая попытка правил — новая версия/run и сравнительная проверка.

## 6. Токены, цена и длительность

Измерения ниже получены из согласованного снимка журнала; живой прогон впоследствии может содержать дополнительные запросы. Источники: metadata физического request journal и saved request bodies, а не размер финального JSON.

Правила интерпретации:

- **Input** — весь фактический запрос: промпты, схемы, статья, контекст, history/ledger, before/diff. Это больше числа токенов слова.
- **Output** включает скрытые reasoning tokens и видимый JSON. Reasoning не прибавлять второй раз.
- **Cached input** — часть input, не отдельная добавка. Сохранённая историческая формула не делает cache discount; это ограничивает соответствие счёту.
- `max_completion_tokens` — потолок reasoning + видимого ответа, а не обещанное потребление. Короткий видимый ответ может стоить дорого из-за reasoning.
- **Логический вызов** может иметь несколько физических попыток. Repair с новым содержанием — другая работа, не обязательно транспортный повтор.
- Неизвестный usage/цена — отдельно; известная сумма не является полным счётом. Стоимость работы Codex-агента/Root не входит в Azure journal этого pipeline.
- Ресурсные Azure Monitor метрики могут включать другие процессы. Их нельзя механически приписать этому run или использовать для заполнения missing usage отдельного request.

Общее правило output/reasoning и cap проверено по [Microsoft: reasoning](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning?view=foundry-classic), caching — по [Microsoft: prompt caching](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching?view=foundry-classic), дата обращения 2026-10-17. Фактические ставки/скидки этой подписки не подтверждены этими страницами.

Не трактовать эти суммы как доказанную полностью устранимую потерю.

Для 1 128 кандидатов все **сохранённые к моменту снимка** стоимости известны; среднее $0,034368, медиана $0,030958, P90 $0,056903. Для 72 кандидатов такая сумма неизвестна. Умножение $0,034368 на десять описывает лишь линейное масштабирование этого неполного смешанного workload, а не бюджет десяти готовых статей.

Основные журналы batches17–20 дают около $0,0150–0,0163 на кандидата по известным сохранённым вызовам, но не включают отдельную направленную recovery-редактуру и имеют иной набор этапов. Сравнение с next1200 не доказывает удорожание одинаковой услуги.

### 6.2 Что можно прогнозировать для 1–10 слов

Без исправлений и дополнительных источников: одна генерация + один core critic + один semantic proposer + один semantic critic = **четыре логических модельных вызова на новый принятый кандидат**. Для десяти — примерно 40, если все проходят и каждому нужен этот полный путь. Root/источники/offline audit — дополнительные трудозатраты, не ещё четыре обязательно платных запроса.

Не каждый кандидат требует нового ядра: корректно подтверждённая навигация может завершиться без новой генерации. Уже готовое предложение с упавшим критиком требует возобновления критика, а не повторной генерации предложения. Существующая принятая статья может требовать лишь конкретного исправления и соответствующего review. Приведённое число — схема хорошего случая, не гарантия расходов/срока и не верхняя граница.

Грубый арифметический ориентир четырёх первых вызовов по средним из таблицы — около **$0,0371 reference на слово / $0,371 на десять**. Он не включает дополнительные repair/retry, работу Root и неизвестный расход, не проверен как тариф или завершённая small-run задача. Сложные identity/source случаи могут существенно выйти за этот ориентир.

Для бюджета полезнее использовать отдельные средние/медианы/P90 по ролям из измерений и долю реальных повторов, чем делить весь смешанный счёт на количество принятых карточек. Полный бюджет задачи включает неуспешные/отложенные кандидаты, обе редактуры и адресные проверки. Время на 10 слов не равно сумме сетевых задержек: независимые кандидаты параллелятся; стадии внутри одного кандидата зависимы, а чтение Root и поиск источников отдельно влияют на срок.

История нужна для выбора версии, а не только для расчёта:

Цена самой генерации выросла ×2,524, но связка high/low против low/low — только на 1,96% по сохранённым reference ставкам. Sol high против low на одних high-статьях стоил ×2,072; убедительного общего превосходства качества не установлено. Нельзя переносить результат отдельного теста переводов на core без своего сравнения.
- [Разбор Editorial Lab](../editorial-lab/reports/editorial-case-studies-2026-10-12/README.md): все шесть политик не прошли заранее заданный validation-барьер; небольшой положительный test-сигнал не отменил этот результат. Не произошло автоматического перехода на «обученного лучшего редактора».
- [Core2735 v5](../editorial-lab/releases/core2735-editorial-v5/README.md): конкретные решения уточнили классификацию, mixed readings и допустимость пустых display-ссылок; это локальные исследовательские решения, не автоматическое обновление generator defaults.
- [reuse-v39](experiments/next1200-batches21-24-v1/editorial/reuse-v39/reuse-pins.json): фактически переиспользованы точные proposer/critic/schema для ограниченного прохода; старый runner сохранён как reference-only. Утверждение о выборе опирается на эти pins, не на название «лучший».

Эти результаты не сопоставимы по одному общему проценту успеха: менялись слова, задания, критерии и этапы. Ни один из них не доказывает, что каждый новый merge лингвистически оптимален.

### 6.4 Где экономить без подмены качества

1. Не отправлять коллекцию целиком: только статью и релевантные owner/expression записи. Сохранять историю ссылками и передавать все значимые обязательства компактно.
2. Не повторять удачные этапы после сетевой ошибки следующего: сначала journal/cache/receipts и raw response.
3. Не вызывать модель ради детерминированного присвоения ID, сборки, сортировки технических файлов и проверки хешей.
4. Разобрать реальные format/closure ошибки нового prompt/version до масштабирования, не ослабляя требования к смыслу.
5. Не повышать effort всем ролям автоматически. [Контролируемый тест 12 слов](reports/REASONING-EXPERIMENT-01.md) показал неоднозначное качество, хотя Luna high стал разумным пилотным выбором. Больше токенов не доказательство лучшего словаря.
6. Сравнивать качество и полную стоимость цепочки, а не цену генерации в отрыве от дорогого независимого критика и последующей редактуры.

## 7. Ошибки, параллельность и безопасное продолжение

В наблюдаемом next1200 policy: глобально 10 физических HTTP, до двух физических попыток на один логический запрос **с общим пулом для transport, JSON и validation retry**, до двух semantic/core revision cycles в своих циклах. Это не «два сетевых плюс ещё два форматных»; отдельный новый recovery после исчерпания требует собственного точного разрешения и наследования учёта, а не обнуления попыток. Общий envelope 10 000 HTTP / $150 **known reference** / 172 800 секунд. Это параметры одного исторического эксперимента, **не универсальные лимиты для новой задачи из десяти слов**. Их нельзя наследовать или сбрасывать без новой зафиксированной политики.

Один владелец execution lock и общий journal/clock/caps предотвращают независимые несогласованные процессы. Внутри владельца работают несколько потоков. Текущий лимит 10 — выбранная политика, а не измеренная Azure-квота запросов в секунду. Параллельность сама по себе не сокращает токены одного запроса.

Unknown usage по текущей политике не блокирует новые запросы. Известная справочная стоимость плюс экспозиция in-flight проверяются; actual unknown сохраняется отдельно, поэтому known cap не ограничивает полный неизвестный счёт. Старый RUNNING описывает STOP/reservations при missing usage — для текущего resilient caller это историческое правило.

Перед resume: проверить процесс/lock, завершённость запросов, точные входы и pins, уже сохранённые результаты. Незавершённая запись in-flight требует reconciliation; «unknown после завершения» — другой случай. Не удалять STOP/lock/result ради запуска вслепую. Не продолжать старый эксперимент с истекшими часами простой правкой clock.

В semantic adapter `None` становится `transport_pending`; исходный result не перезаписывается, поздние результаты имеют retry-версию. Принятое предложение/критик переиспользуются только при точном совпадении входов и доказательств. Подробности — [PROJECTION-AND-RESUME002](experiments/next1200-batches21-24-v1/editorial/PROJECTION-AND-RESUME002.md).

## 8. ID, принятие и сохранение

- Candidate UUID принадлежит реестру. Local keys модели — не глобальные UUID и не номера значений Van Dale.
- Уже присвоенные unit/sense IDs сохраняются. Нельзя повторно `freeze` полутрекированную статью с новым namespace.
- В actual assigned generation shape примеры — строки. Editorial projection добавляет им UUIDv5 от **существующего sense UUID**, имени `editorial:example:v1:<zero-based-position>:<exact-text>`. Уже трекированные example objects сохраняются.
- Merge получает разрешённый новый sense ID и историю исходных ID/определений. Исходные примеры/ограничения не исчезают. Перенумеровать отображение «1, 2, 3» позже можно отдельно от постоянных IDs.
- `model_ready` — лишь прохождение модельного цикла; `ready_for_root` — готовность редакторского результата к Root; `accept_generation_for_editorial` — ядро принято для следующего прохода; `accept_editorial` — отдельное принятие редакторского результата.
- `human_approved` остаётся false без фактического человеческого чтения. Research acceptance не равно `import_ready` и не даёт разрешения на публикацию/импорт.

Для каждой попытки хранить inputs, sources/prompts/schema/runtime pins, собранные request/response bytes, request IDs/HTTP/errors/usage, chain/diffs/ledger, сырую и assigned статьи. Для каждого принятия — точные article/history/review pins, автор/метод, открытые замечания, разрешение research-only. Не переписывать ответы провайдера, старые accepted snapshots и исторические дефектные версии.

Логический состав новой небольшой задачи (точные команды и две реальные структуры core/semantic описаны в [README v2](scripts/card_pipeline_v2/README.md)):

```text
runs/<new-small-run>/
  inputs.json                 # точные 1–10 кандидатов, scope, contexts
  preflight.json              # версии, собранные сообщения, limits
  source-snapshot/            # минимальные исходники/промпты/схемы
  journal.sqlite3             # каждая физическая попытка
  payloads/                   # запросы/ответы без секретов
  candidates/<candidate-id>/  # статьи, critic, ledger, diff, lineage
  acceptance/                 # реальные решения редактора
  editorial/                  # proposer/critic, change_log, concerns
  assembly/                   # новая research-версия и manifest
  report.json                 # все исходы, проверки, known/unknown cost
```

Имена каталогов здесь предлагаются для переносимого запуска. Исторические runs используют разные структуры — конвертировать их автоматически по этой картинке нельзя. Не копировать node_modules, окружения и всю базу в каждый кейс; сохранять только нужные версии и доказательства.

## 9. Как передать задачу другому агенту

Шаблон задания, который можно заполнить без истории чата:

> Обработай явно перечисленные candidate IDs/леммы [список] в новой исследовательской папке [абсолютный путь]. Сначала проверь существующих владельцев и предыдущие попытки. Используй этот регламент, закреплённые core generate/revise/critic и semantic proposer/critic; перед API предъяви воспроизводимый preflight и версионированную политику маленького запуска. Не запускай историческую партию и не меняй frozen файлы. Генерируй оригинальное современное учебное ядро, закрывай required issues явно, сохраняй optional и identity gaps. После core-приёмки проведи ограниченную semantic-редактуру и адресный аудит повторяющихся выражений. Сохрани полные статьи/историю/ID, ответы/ошибки/usage, отдельные решения и новую research-сборку. Отчитайся по каждому входному кандидату; не называй unresolved готовой статьёй. Приложение, БД, импорт, master progress/defaults не менять. Не отправляй всю коллекцию в prompt. Бюджет/параллельность: [явно задать]. Ответственный за окончательную редакторскую приёмку: [указать].

Здесь Root означает ответственную роль приёмки, а не обязательное присутствие именно нынешнего чата. Другой уполномоченный агент может исполнять эту роль, но должен принять конкретное содержимое и сохранить доказательства; чужую подпись или человеческое одобрение он не выдумывает.

### Текущая обвязка v2

Использовать [README и команды v2](scripts/card_pipeline_v2/README.md). Код общий для партий; каждый запуск создаёт новые manifests, input/source pins и budgets. Подготовленные runs исполняют frozen copy своего кода. Для следующей партии меняются входы и конфигурация; переписывать скрипт под слово или исправление не нужно.

- [core.py](scripts/card_pipeline_v2/core.py): prepare → generation/critic/до двух исправлений существующим runtime → явная core acceptance после чтения.
- [editorial.py](scripts/card_pipeline_v2/editorial.py): принятые ядра → editorial templates и manifest с сохранением unit/sense IDs и присвоением example IDs.
- [cli.py](scripts/card_pipeline_v2/cli.py): prepare → semantic proposal → отдельный critic именно нового предложения. Workflow и сравнительный validation — разные режимы.
- [finalize.py](scripts/card_pipeline_v2/finalize.py): отдельная Root acceptance и assembly с research_only=true, import_ready=false.
- [recover.py](scripts/card_pipeline_v2/recover.py): явное continuation после reconciliation, сохранение успехов, часов, бюджета и резерва для неизвестного расхода.
- [report.py](scripts/card_pipeline_v2/report.py): offline audit запросов, состояний и справочной стоимости.

Нынешний semantic workflow не скрывает неуспех автоматическим repair: rejected/invalid результат остаётся для Root. Содержательную доработку выполняют в отдельной явной попытке с новым proposal и свежим critic либо через прежний bounded adapter. Автоматический semantic repair в общем интерфейсе ещё не реализован; core repair переиспользуется полностью. Редакторское чтение и owner/expression reconciliation не заменены pass-флагом модели.

Встроенная проверка core допускает packets до 300 кандидатов; фактическое API-исполнение новой обвязки проверено на одном fresh ядре и десяти reused ядрах в semantic A/B. Это не нагрузочная проверка партий 50/100/300.

`--limit 10` в старом batch CLI не выбирает десять новых слов. Не запускать historical prepare_batch20 для новой небольшой задачи.

## 10. Ограничения достоверности

Проверка опирается на доступные сохранённые локальные версии и запросы, а не на воспоминание чата. Исторические источники охвачены по фазам: пилот/правила, reasoning A/B, поздний batch20, next1200, отдельная semantic редактура и recovery. Полный пересмотр лингвистического качества всех статей или всех текстов запросов целью документа не является.

Восстановление исторической выборки тоже имеет границу: точные `selection-v2` inputs/proof закреплены, но отдельный постоянный preparer-скрипт этой выборки проверкой не установлен. Поэтому воспроизведение закреплённых входов и повторное вычисление отбора с нуля — разные обещания.

Известен узкий исторический случай overwritten reconciliation005: он оформлен отдельным Root exception с точным path/старым hash и пометкой недоступности, не выдается за успешную проверку утраченного файла. Новому агенту запрещено обобщать это на другие pin mismatches: несовпадение требует разбора, исходные данные/ответы/решения сохраняются.

Справочная цена не подтверждает Azure invoice. Пропавший usage не восстановлен. Обвязка v2 реализована в указанном объёме; выборка десяти слов и одна fresh канарейка не доказывают качество для произвольных слов/выражений. Успех критика не гарантирует полноту словаря, а классификация `uncertain` и scoped acceptance не должны маскироваться под отсутствие вопросов.

## 12. Проверка v2 на десяти словах и новая инструкция

18 октября 2026: [отчёт по десяти словам](reports/ten-word-optimization-20261018-v2/REPORT-RU.md), [исходное согласование](../../docs/discussions/2026-10-18-02-ten-word-validation-and-reusable-runner.md), [точные команды](scripts/card_pipeline_v2/README.md).

Для нового research запуска использовать v2, а не переписывать `pilot.py` под новую партию:

1. Зафиксировать список и candidate IDs; проверить точные совпадения, формы, варианты, существующие статьи/выражения и owner. Решение reuse/new/repair/unresolved сохранить с источниками. Сетевой поиск и регистрация supplemental candidate пока выполняются агентом до runner.
2. Подготовить новый packet и manifests с бюджетом, источниками и scope. Prepare замораживает код и проверяет inputs/pins; API до этого не вызывается.
3. Для нового ядра выполнить core run: Luna high, Sol low, до двух исправлений. Для уже принятого ядра переиспользовать его exact acceptance/history вместо платной повторной генерации.
4. Root читает полную конечную статью, критику, ledger и lineage; core acceptance оформляется отдельно. Подпись не выводится автоматически из model_ready.
5. Собрать editorial manifest. Неявный режим сохраняет full/high. Compact/high, full/low и compact/low задаются явно; одно слово не является доказательством их эквивалентности. Compact применяется только к semantic stages, не к core.
6. Compact сохраняет полные определения/примеры/грамматику, все corpus texts/target spans/IDs, полный critical ledger, Root changes и source obligations. Полные provenance metadata и history path остаются в pinned artifacts. Если metadata определяют смысл, авторитет или границы источника, выбирать full, а не удалять их автоматически.
7. Выполнить proposal и новый critic фактического предложения. Schema/hash failure не является accept. Не исправлять model-returned hash молча. Rejected/invalid semantic result остаётся отдельным исходом и требует явной bounded доработки с новой критикой; v2 workflow не скрывает это автоматическим повтором.
8. Root читает новый результат; записывает отдельную accept_editorial только с exact proposal/critic pins. Собирается отдельный research manifest с import_ready=false. Чтение каждой статьи растёт с размером партии; подготовка общего кода не повторяется на каждое слово.
9. Unknown usage хранить как unknown. После transport failure — отдельное continuation с сохранением старых records, clocks, budgets и резерва за каждый неизвестный физический вызов. Успешные ответы не повторять.
10. Отчёт должен показывать стоимость каждого вызова, все failed/invalid outcomes, исходную и конечную статьи, diff, качество positive/negative controls и границы вывода. Стоимость Root и Azure invoice не выдумывать по token reference.

### Решение по оптимизациям

На этой выборке все 40 proposals сохранили статьи, все 40 actual critics приняли их с корректными hashes, все 16 содержательно ошибочных merges отклонены. Но один frozen-reference response в compact/high содержит неправильный article hash и остаётся невалидным. Поэтому общая безопасность full/compact и high/low не объявлена доказанной, а оптимизированный профиль не заменяет implicit default.

Reference средняя semantic пара: full/high $0.0187816; full/low $0.0177966; compact/high $0.0168762; compact/low $0.0159132. Это снижение 5.2%, 10.1% и 15.3% соответственно; **не цена полной карточки**. Отдельная канарейка denkfout прошла fresh generation, core critic, две явные Root acceptance, semantic proposal/critic и assembly. Семантический repair loop и выражения этой новой обвязкой не проверены.

Кэш не назначается экономией по одному cache key. Для качественного A/B он отключён; для повторного использования нужен действительно общий достаточно длинный prefix. Проверять фактические reads/writes и тариф; не добавлять padding ради порога. Подробный межсловный результат и известные ошибки находятся в отчёте.

## 13. Содержательные правки и обязательный cache preflight

Продолжение18октября2026: [отчёт](reports/targeted-edits-20261018-v1/REPORT-RU.md), [план и ожидаемые решения](../../docs/discussions/2026-10-18-04-targeted-edits-and-cache-preflight.md). Вместо проверки только unchanged статей применены четыре диагностических случая: реально избыточное разделение одного значения, допустимый merge, тонкая потеря смысла в том же merge и сохранение прочих значений. Оценивать отдельно schema/hash validity, сохранение смысла, выполненную полезную правку и рецензию. Не считать отсутствие merge автоматически смысловой ошибкой, а совпадение verdict — доказательством качества. Fixture namespace и synthetic history не являются accepted dictionary identity.

Cache prepare теперь блокируется, если общая system часть не одинакова или короче probe threshold. Счётчики216/682 o200k_base для critic/proposer — estimates без точного deployed mapping; обе инструкции далеко ниже1024. На них не запускать новую paid межсловную серию. Если полезный общий контракт действительно длиннее, после preflight сначала выполнить ограниченный cold/warm probe и проверить реальные reads. Padding запрещён; добавление новой общей schema меняет prompt и расход, а не даёт бесплатную экономию. Кэш повторного контекста одного слова и кэш общих инструкций разных слов — разные случаи. Старые frozen runs сохраняют свои версии.

### Фактический результат продолжения

Все16случаев слово×режим выполнили требуемое объединение; все16gold и16тонких negative controls получили ожидаемые рецензии. Смысловые различия в проверенных правках сохранены. Один первоначальный compact/high response оказался schema-invalid (coverage_notes:list вместо string), потребовал отдельного исправляющего вызова и свежего critic. Первоначальный ответ и его цена сохранены. Поэтому стоимость сравнивается после восстановления, а не только по успешным calls.

Средняя ordinary цена в fixed reference: full/high $0.031808; full/low $0.0297415; compact/high **$0.0353635 с repair**, compact/low $0.0264755. На этой серии compact/high оказался дороже на11.2%, compact/low дешевле на16.8%. Это четыре диагностических кейса, не стабильная частота отказов и не гарантия corpus-wide качества.

Для следующего небольшого research word-editing batch допустим явный профиль compact-low с Root/validators; неявный default и production не переключены. High не продемонстрировал преимуществ по смысловым контрольным задачам и не исключил format failure. Новая [версия proposer prompt](scripts/card_pipeline_v2/prompts/proposer-v2.1.txt) уточняет string-типы полей журнала; её pin использовать в новых configs. Одна fresh compact/high canary без истории ошибки прошла; старые prompts не переписаны. Точное описание результатов, полный расход и ограничения — в [итогах](reports/targeted-edits-20261018-v1/README.md).


## 14. Новые входы: подготовка через локальный поиск v2

Применять к новым подготовкам после этого обновления. Текущие замороженные партии и их source snapshots остаются на своих версиях; повторную генерацию уже принятых статей это не запускает.

Входной адаптер [prepare_inputs.py](scripts/local_search_v2/prepare_inputs.py) принимает pinned свежий seed packet, pinned индекс и upstream selection decision с baseline evidence. Он не заменяет проверку словаря, текущих назначений и reservation. Результат — отдельные inputs, полный evidence archive, проверенные target spans и source offsets, код/источники/selection pins. Инструкция и формат config: [PREPARATION](scripts/local_search_v2/PREPARATION.md).

С `--core-manifest` и `--core-run` адаптер создаёт новый manifest и вызывает прежний core.prepare. Полный архив и proof включаются в проверяемые evidence pins; в модельный контекст идут только выбранные фрагменты. API не вызывается. Успешная подготовка не является разрешением execute: это остаётся gate общего coordinator.

Если обязательное свидетельство потеряно при отборе — увеличить лимит/закрепить контекст. Если обязательного свидетельства нет или выдача пустая — required issue и отдельное решение по источникам до подготовки core-run. Не удалять такие IDs молча, не принимать отсутствие находки за отсутствие слова. Обычные внешние источники и recovery не выдавать за train-контекст.

[Проверка совместимости](reports/local-search-preparation-20261018-v4/smoke-result.json): существующий проверочный seed прошёл новый поиск и core.prepare, старые inputs/article сохранены, STOP исключает исполнение fixture,0API. Это не нагрузочный запуск300 и не доказательство полноты значений.

## 15. Заметка, дополнительное значение или статья

Применять [порядок редакторских решений](EDITORIAL-EVIDENCE-DECISIONS.md). Сочетаемость — usage_note, грамматическая информация при той же идентичности — grammar_note. Они принимаются как отдельные research sidecars после независимого критика и Root, а не автоматически вписываются в essential_grammar.

Предполагаемое дополнительное значение — sense_gap; другая лемма/омоним/выражение — article_candidate. Сейчас это очередь с точной исходной статьёй, evidence pins, контрастом и вопросом владельца. Новые sense/article IDs не создаются этим шагом. Подтверждённое значение позже проходит отдельное исправление ядра с полной статьёй, lineage, критикой и Root; подтверждённая новая статья — регистрацию кандидата и обычный core-цикл. Merge-only semantic контракт не расширять незаметно.

[Машинный валидатор sidecar](scripts/local_search_v2/editorial_decisions.py) проверяет исходник, цель, context IDs, допустимый статус и привязку критики/Root к точному черновику. Он не генерирует текст, не доказывает содержательную правильность, не меняет статью и ничего не импортирует. Создание новых значений и статей в этом обновлении не автоматизировано.

Основание: [опыт пользы поиска](reports/retrieval-editorial-benefit-20261018-v2/REPORT-RU.md).
