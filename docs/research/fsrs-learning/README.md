## Что уточняется по первоисточникам

В Anki короткие учебные шаги могут работать вместе с FSRS. На шаге обновляется состояние памяти FSRS, а время ближайшего показа может задаваться настройкой шага. После завершения шагов используется дальнейшее расписание. Код `LearnState::answer_again/answer_good` получает `fsrs_next_states.*.memory` даже при наличии фиксированного короткого шага. Поэтому объяснение «FSRS впервые подключается только после обучения» неточно.

Источники, проверенные 2026-09-08:

- [Anki: FSRS и Learning/Relearning Steps](https://docs.ankiweb.net/deck-options.html#learning-and-relearning-steps): короткие шаги совместимы с FSRS; пустые шаги позволяют передать краткосрочное расписание FSRS, документация обозначает этот режим экспериментальным.
- [Anki: learning.rs](https://github.com/ankitects/anki/blob/main/rslib/src/scheduler/states/learning.rs): обновление FSRS memory state внутри учебных шагов.
- [Anki: Simulator](https://docs.ankiweb.net/deck-options.html#the-simulator): прогноз нагрузки зависит от состояний карточек, параметров и допущений.

Оговорки к PDF: не следует принимать без дополнительной проверки обещание, что дополнительный короткий шаг обязательно улучшит долговременную память. Предложение скрывать learning через пустую stability смешивает модель памяти с интерфейсным состоянием. Вариант B игнорирует первую оценку в FSRS и не эквивалентен варианту A. Фраза «5 часов, вероятно, предназначены для забывания уже выученного» не описывает нашу формулу: 0.212 — отдельный начальный параметр для первой Again. Даже 15 минут могут пересечь полночь; длительность и календарный день требуют отдельных тестов. В PDF есть полезные вопросы, но его реализационные рекомендации нельзя переносить буквально.

## Локальное воспроизведение

Запуск из корня репозитория:

```sh
psql postgresql://postgres:postgres@127.0.0.1:54322/postgres -X -f scripts/diagnostics/learning-observability.sql
```

Сценарий вызывает настоящие SQL-функции Start Learning, review, статистики, истории и выбора карточки. Создаёт одноразовые записи и пользователей внутри транзакции; в конце ROLLBACK. Для проверки ожидания «Learn увеличивает New» добавить `-v enforce=1`: на исследованной реализации команда завершается с кодом 3 и сообщением `PRODUCT EXPECTATION FAILED: Learn does not increment the New counter`. Это намеренно красная проверка, исправления здесь нет.

| Действия | FSRS-оценённых карточек | История | New на экране | Срок |
|---|---:|---:|---:|---|
| 5 × Learn | 0 | 0 | 0 | все 5 доступны сразу |
| Затем первая Good для 2 из 5 | 2 | 2 | 2 | 3 ещё доступны сразу |
| Затем первая Good для оставшихся 3 | 5 | 5 | 5 | примерно 2.3065 суток |
| 10 / 50 / 100 × Learn | 0 | 0 | 0 | все доступны сразу |
| Затем первая Good для всех | 10 / 50 / 100 | 10 / 50 / 50* | 10 / 50 / 100 | примерно 2.3065 суток |
| 5 первых Again напрямую, как проба предложения | 5 | 5 | 0 | 0.212 суток, около 5 ч 5 мин |

*History возвращает максимум 50 записей и `has_more=true` для 100; это не потеря остальных оценок.

Последняя строка вызывает review RPC напрямую, обходя V2-запрет оценки новой карточки. Это проверка эффекта на данные, не реализованный пользовательский сценарий. Все действия происходят в одной транзакции без продвижения времени. Массовые Learn вызываются напрямую, поэтому этот тест не доказывает соблюдение дневного лимита в UI.

Причина счётчика: `get_detailed_training_stats` требует и первую запись `review_type=new`, и текущий интервал `>=1 день`. Start Learning не создаёт запись оценки, а первая Again даёт интервал меньше суток. Простая замена Learn на Again не исправит New.

Состояния: после первого Good FSRS уже записан, но `in_learning=true` остаётся. V2 показывает learning, тогда как срок составляет несколько дней. Это доказанное расхождение признаков; оно не доказывает, что FSRS не работает или карточка навсегда застряла.

## Ограничение среды

Обнаружено локальное расхождение определений функций: public `get_next_card` делегирует `get_next_card_without_known`, хотя миграция 123 в исследованном коде задаёт вызов `private.training_scheduler_candidates_v1`. Прямой вызов private selector после Good возвращает practice, public wrapper — review. Диагностический скрипт показывает обе колонки. Порядок показов онлайн этой проверкой не установлен. Нужна отдельная чистая тестовая база из проверенной последовательности миграций и сверка определений реально установленных функций. Сбрасывать существующую общую локальную базу в этом срезе не стали.

## Направление работы

Learn → Again остаётся кандидатом. Приоритет — понятная история начала обучения, счётчик начатых сегодня карточек, объяснимый срок и причина следующего показа. Исправление этих измерений может оказаться достаточным без изменения расписания.

Начатые, но ещё не оценённые карточки включить в тесты обоих вариантов; миграция потребуется только при принятии нового поведения. Не добавлять фиктивные прошлые оценки.

Пользователь ожидает, что явно созданная для обучения карточка сразу окажется в обучении. Для сохранённого выбранного результата следует обеспечить единое пользовательское действие сохранения и добавления в обучение. Это не доказывает, что была попытка вспомнить. Промежуточные варианты генерации и отклонённые кандидаты не должны скрыто создавать оценки или несколько учебных карточек. Сверить с ADR 0002 и реальными клиентами; при необходимости скорректировать контракт явно.

## Моделирование: два разных результата

1. **Проверка работы программы:** настоящие серверные обработчики, искусственное время, заданные ответы, воспроизводимый порядок выбора. Прогон выдаёт таблицу событий: показ → действие → сохранение → история/счётчики → назначенный срок → фактический повтор → причина задержки/исключения. Это проверяет нашу программу, а не эффективность памяти.
2. **Прогноз нагрузки:** модель ответов и затрат времени на 30/90/180 дней. Указать размер коллекции в значениях × направлениях, новые в день, частоту занятий, пропуски, целевое удержание и время чтения/ответа. Выдавать диапазоны нагрузки, просрочку и количество активных карточек. Не использовать один и тот же FSRS как единственную модель памяти и расписания для доказательства превосходства FSRS.

Обязательная матрица будущего прогона:

| Сценарий | Проверяем |
|---|---|
| 5 новых + 10 повторений | начало обучения считается один раз, повторения не теряются |
| Только 10 новых | видны ли их повторения в этом режиме; что означает фильтр |
| Закрыл после 2 из 5 | восстановление после открытия; 3 незавершённые не теряются |
| 50/100 новых за день | лимиты, нагрузка и ограничение History, без скрытой потери событий |
| Утро/вечер; пропуск 1/3/7 дней | фактический срок и просрочка |
| 23:55 и переход времени | сутки пользователя, короткие интервалы, DST |
| Несколько Again; Hard/Good/Easy | выход из короткого обучения и корректный расчёт памяти |
| Known и отмена в разных состояниях | сохранение расписания и исключение из очереди |
| Два значения, два направления | независимая идентичность и честные счётчики |
| Повтор запроса, потеря ответа, сбой следующей карточки | оценка сохраняется один раз |

Управляемое время: сначала определить все использования now/current_date/clock_timestamp и случайного порядка. Для сравнения реализовывать часы/seed на тестовом уровне и проверять соответствие настоящим RPC. Не переводить глобальные системные часы и не писать отдельную упрощённую копию планировщика, выдавая её за приложение.

Прогноз затрат: сумма времени первых знакомств, попыток вспомнить, чтения ответа и взаимодействий. Например, 1000 карточек при 10 новых в день требуют минимум 100 учебных дней только для первого знакомства; это не срок окончательного запоминания и не включает повторения. Длительность ответа и вероятность ошибок сейчас не измерены, поэтому достоверный персональный прогноз минут ещё не рассчитан.

Общее исследование «какой алгоритм лучший» сейчас не блокирует работу. Если заказывать дополнительное исследование, использовать [узкий запрос](research-brief.md).
