Координация и живой статус: https://github.com/vbalashi/2000nl/issues/533.

Это план для обсуждения. Запуск агентов, изменение продукта и развёртывание ждут отдельной отмашки владельца. Сейчас разрешены исследование кода, формирование задач и сохранение плана. Ниже кандидаты решений явно отделены от уже заданных требований.

## 1. Приоритеты и охват

| Порядок | Приоритет | Результат | Зависимости |

## 3. Поток A: загрузка, кэш и непрерывность экранов

Владелец: senior frontend/performance engineer; при подтверждённой серверной причине подключается специалист по API/SQL отдельным срезом.

### A1. Первый список Library

1. На согласованном Chrome-профиле Nikolai записать чистый вход после reload и первое открытие Library, затем ручной Retry. Не менять учебное состояние владельца. Сохранять обезличенные request ID, статус, error kind, длительность auth/HTTP/DB/validation и момент появления 50 строк.
2. Разделить гипотезы: auth/session readiness; холодный API/SQL; первый или второй cursor-запрос; несоответствие ответа контракту; отмена/смена scope; конкуренция preload и открытия. Для каждой — способ опровержения и результат. Особенно проверить частичный успех: первая порция пришла, следующая не пришла.
3. Прогрев запускается после готовности пользователя, языка и material scope. Один владелец загрузки, один ключ, дедупликация открытия и фонового запроса. Грузить только первые 50 строк/групп и необходимые метаданные; оценить стоимость нынешней полной article projection, не тянуть 14 тысяч статей и не регенерировать переводы. Полные детали — по выбору слова либо отдельной обоснованной стратегии.
4. При готовом кэше показывать его сразу. При первом пустом кэше сохранять рамку экрана, поиск и скелет списка. Ошибка не должна показывать ложные «0 matching articles» и фиктивную пагинацию как достоверный результат.
5. Ограниченный автоматический повтор только для подтверждённо временных ошибок: сеть, 408/429 с Retry-After, выбранные 5xx. Кандидат: один повтор с короткой задержкой, не бесконечный цикл. Отмена при новом запросе/выходе из аккаунта. 400/403/contract mismatch не повторять вслепую; 401 обрабатывать в общей auth-границе. Retry безопасен для read-only POST, не распространять правило на мутации.
6. Таймаут менять только после измерения этапов и общего бюджета; увеличение само по себе не решает пользовательское ожидание. Не записывать ошибку в успешный кэш и не терять успешные данные после неудачного обновления.

Приёмка: не менее 10 новых browser contexts/холодных входов и 20 тёплых возвратов в контролируемой среде; отдельная ограниченная production-проверка. При готовом кэше первая строка видна <=100 мс после принятого клика как целевой бюджет, с p50/p95 и указанием среды. Первый load report содержит end-to-end timings; для холодного запроса SLA утверждается по измерению. 50 строк без дыр/дубликатов и правильный курсор. Тесты auth-delayed, 5xx→success, two-page partial failure, permanent failure, query switch, logout/account switch, revoked source.

### A2. Statistics и Activity

Сохранить предыдущий успешный read-model в пределах account+language+filter+date-range/timezone. Разделить initialLoading и refreshing. При возврате сначала рисовать сохранённое, обновлять без замены блоков loader-ом. Обновление после accepted grade/undo/learning action/session completion должно инвалидировать нужный read-model; сам refresh не должен перерисовывать/сбрасывать текущую карточку. Сохранить выбранный период, материал и scroll. При смене аккаунта старые данные не видны.

Кандидат общего принципа: хранение в памяти текущего аккаунта и дедупликация чтений. Не начинать с общей новой cache-библиотеки или переписывания всех запросов. TTL может отличаться от Library; изменённые действиями данные важнее произвольного одинакового TTL. Предзагрузка Statistics — низкий приоритет после Library, только если не конкурирует со стартом тренировки.

Приёмка: готовые блоки остаются при повторном входе и при ошибке background refresh; первый вход имеет устойчивую общую разметку; действия пользователя отражаются после подтверждения сервера. Network evidence для обоих endpoints и отдельного журнала Activity.

### A3. Training continuity

Записать последовательность состояний active destination / bootstrap / current owned session на Library→Training→Statistics→Training. На готовой сессии сохранить карточку и её сторону; не показывать Preparing Training из-за фонового refresh. Настоящее восстановление/ошибка остаются различимы. Покадровая запись/DOM transition assertions, не только конечный screenshot. Покрыть пустую, активную, завершённую сессию, resume и медленную сеть.

## 4. Поток B: действия обучения и типы упражнений

Владелец: senior domain/session engineer. UI обязан следовать одному Platform/DB контракту; запрещено вести «настоящую» очередь только в клиентском ref.

### B0. Сначала таблица семантики

Для Words, Idioms, Translation и Word in Context записать: видимый Face, ожидаемый Answer, исходный/целевой языки, точный Exercise Target, направление, FSRS identity, единицу session count, применимость Learn и дополнительного действия. Использовать один реальный пример на каждый вариант. `CONTEXT.md` уже различает meaning, attached idiom и exact example node; не объединять прогресс братьев/направлений случайно.

### B1. Оценка прямо в Library — уточнение владельца

Владелец отверг мини-сессию и дополнительную карточку. Новая целевая схема: «Хочу учить» включает конкретную цель в обучение и показывает четыре привычные оценки прямо под текущим значением. Для уже изучаемой цели оценки доступны в статье без Train Next. Не создавать приоритетную очередь, не переключать экран, не приостанавливать активную тренировку ради отдельного запуска. Это уточнение плана, не разрешение на реализацию.

Важная новая P1-проверка: владелец оценил `pijn` в Activity, но Library показывает New у обоих значений; первое имеет Train next, второе Learn. Сначала сопоставить точные entryId/meaning/cardTypeId/content node из Activity и Library. Одинаковое написание не доказывает одинаковую учебную цель; состояние другого значения или направления может законно отличаться.

В коде подтверждено: `librarySenseCardModel` сводит отсутствующий `entry.card.scheduler.repeatCount` к 0. `LibrarySenseCardGroup` показывает New при отсутствии undoKnown и repeatCount=0. Таким образом, New сейчас не является полноценным отражением учебного состояния: «начал учить, но ещё не оценивал», «нет прогресса этого направления» и «card отсутствует в projection» могут выглядеть одинаково. Это объясняет риск неверной надписи, но не доказывает причину конкретного production-расхождения. Нужна трасса точной цели, owner и состояния, включая cache invalidation после оценки.

Предлагаемый контракт для обсуждения: после Learn статус «Изучается», четыре стандартные оценки Again/Hard/Good/Easy; подтверждённая оценка обновляет тот же авторитетный прогресс и срок повторения, что и Training, и отображается в Activity с происхождением Library. Learn сам по себе не подставляет оценку Good. Не смешивать последнее действие/оценку, текущий статус, число повторений и следующую дату: это разные данные. Отсутствующий или загружающийся state не маркировать New.

Оценка из открытой статьи — явная самооценка при видимом ответе. Не записывать её как прохождение теста со скрытым ответом. Существующая Platform action boundary и идемпотентность сохраняются; не добавлять клиентскую запись FSRS. Никаких скрытых оценок при чтении и никакого автоматического переноса одной оценки на все значения, направления, идиомы или примеры.

Согласовано владельцем: четыре кнопки в Library оценивают выбранное значение в направлении «слово → определение». Обратное направление и вложенные упражнения сохраняют отдельный прогресс. Первое знакомство с новым значением должно показывать слово и определение до обратного задания. Нажатие «Хочу учить» означает намерение учить значение в обоих направлениях, без автоматической оценки обратного. Чтение само по себе не должно скрыто записывать учебное действие. В сценарии Library явное Learn после открытого слова/определения может фиксировать знакомство; не добавлять без согласования требование сначала обязательно поставить Good или пройти отдельную сессию. Согласовано владельцем: обычный уход в Library сохраняет сессию. После внешней учебной оценки при возвращении в Training пересчитывается только оставшаяся часть по актуальному прогрессу; уже принятые ответы сохраняются. Оценка в Library не засчитывается автоматически как выполненный член текущей сессии. Цель не удаляется безусловно: после Again она может снова оказаться в остатке, если наступил срок повторения. Сохраняются рецепт, материал, выбранные направления и размер оставшейся части, насколько позволяет доступный пул; если его недостаточно, не расширять фильтры скрыто. Механизм инвалидирования/версии состояния и атомарного обновления остатка — проектируемая реализация, не существующая подтверждённая возможность. Обязательно проверить межустройственный resume/ownership, идемпотентность, одновременные ответы, отмену оценки и отсутствие двойного прогресса. После ответа достаточно компактного подтверждения с возможностью исправления через существующий авторитетный undo-контракт, если он применим; постоянный верхний баннер не нужен.

Проверка исходников 2026-10-02: миграция 138 `start_learning_entry_card` включает выбранное и парное ordinary-направление: fsrs_enabled/in_learning=true, для нового next_review_at=now; обратному задаёт seen_count=0 и last_seen_at=null. Оценка, stability/difficulty и review history не копируются. В схеме 042 ещё не оценённая цель имеет fsrs_reps=0, fsrs_last_grade=null, fsrs_stability/fsrs_difficulty=null. Это не оценка Again/Hard/Good/Easy по умолчанию. Первый настоящий grade инициализирует собственные параметры. Selector 160 классифицирует такую включённую due-цель как learning, а ограничение new-direct не является доказательством строгого порядка после Learn. Проверить фактическую цепочку первого знакомства; не обещать, что уже существует отдельный gate «сначала оценка direct».

Обратная цель участвует в подходящей Words-тренировке с обратным или обоими направлениями либо в согласованном Translation как контекстном предъявлении той же reverse-цели, нужным материалом/фильтрами и политикой отбора. Она не превращается в идиому/перевод предложения и не вставляется автоматически в уже зафиксированный finite plan. «Включено в обучение», «ещё ни разу не оценено» и «сейчас входит в сессию» — разные состояния.

Приёмка: Activity→Library для той же точной цели показывает согласованный state; разные значения/направления не смешиваются. Learn→Learning без фиктивного grade; четыре оценки доступны прямо в статье; один клик даёт одно действие, корректный новый due и историю. Refresh/retry/двойной клик/смена устройства не дублируют review. Проверить активную сессию, оценку раньше due, undo, отсутствующий card state, ошибки чтения/сохранения и инвалидирование Library/Statistics. DB/RPC characterization обязателен перед изменением контракта. Реализация ждёт отмашки.

### B2. Один Translation и оба направления идиом

Уточнение владельца: нужен **один** режим Translation. Показываем перевод предложения/примера и вспоминаем ключевое слово конкретного значения. Оценка идёт в обычный `definition-to-word` этого значения. Согласовано владельцем: отдельный перевод целых предложений с собственным FSRS остаётся на паузе и скрывается из выбора новых тренировок. Его реализацию и существующую историю сохраняем для возможного будущего возврата; не удаляем и не переносим прогресс автоматически. Предыдущий вопрос координатора о двух заданиях был излишним: это уже принято 2026-09-25 в [ADR-0015](../adr/0015-word-in-context-shared-reverse-state.md) и [обсуждении](../discussions/2026-09-25-03-word-in-context.md).

Трасса исходников: builder одновременно перечисляет family `sentence` (видимое Translation) и `word-in-context` (видимое Word in Context). Контроллер первой ветки вызывает `startTranslationSession`, второй — `startTrainingSession` с `[definition-to-word]` и `presentationMode=word-in-context`. Вторая ветка использует `TrainingSenseCardV2Session`, обычные capabilities и `performPlatformV2TrainingAction`; пример/подсказка записываются как evidence, не как новый FSRS target. Отдельная sentence-ветка была опубликована с включённым флагом в commit `8e861949` / PR #501; контекстный путь добавлен позднее (PR #511), но оба пункта остались в builder. История доказывает сосуществование двух путей, а не переименование одного идентификатора.

Пустой Direction: sentence scenario объявляет word-to-definition, но ApprovedTrainingBuilder фильтрует sentence до definition-to-word. Для желаемого Translation нужно показывать правдивое фиксированное направление «Перевод примера → слово» и конкретный пример ответа ключевым словом; не оставлять пустую секцию и не изображать несуществующий выбор direct/reverse.

Реализация после отмашки: убрать самостоятельный sentence-пункт из выбора новых упражнений; переименовать видимое Word in Context в Translation / «Перевод» во всех локализациях. Внутренний presentationMode можно сохранить — переименование UI не требует смены identity или нового расписания. Обновить summary, примеры Face/Answer, сохранение и восстановление рецептов. Старые sentence-сессии/пресеты/историю инвентаризировать отдельно: не стирать историю и не конвертировать sentence FSRS в reverse автоматически. Совместимость и прекращение старых запусков должны иметь явный проверенный путь.

Приёмка: ровно один Translation в builder; перевод примера→раскрытие ключевого слова/значения; один реальный grade изменяет только reverse exact meaning, не direct, не соседнее значение, не самостоятельный example target. Проверить все четыре оценки, duplicate/retry, Activity, due/reps, resume, translation off и длинные примеры. Существующий DB-test `trainingWordContextEligibility` доказывает ordinary reverse membership и start-learning без sentence schedule, но не заменяет свежую проверку **review-card** и фактического изменения FSRS по четырём оценкам.

#529 остаётся существующей задачей идиом: genuine mixed sessions во всём пути draft→save→plan→card→grade→resume→completion. Обе выбранные кнопки дают обе реальные разновидности, с канонической идентичностью направления и отдельным прогрессом. Это независимо от единственного фиксированного направления Translation.

## 8. Прожарка: очередь решений

По одному вопросу, с рекомендацией и конкретным примером. Технически доказуемые пункты не перекладывать на владельца.

1. **Решено:** кнопки Library оценивают конкретное значение в прямом направлении; Learn включает намерение учить оба направления, первая встреча — слово/определение. Обратное и вложенные упражнения не получают скопированную оценку. Мини-сессия отвергнута, приоритетная очередь не выбрана.
2. **Решено:** внешняя учебная оценка инвалидирует остаток; при возврате пересчитать его без потери принятых ответов. Простая навигация не сбрасывает сессию. Внешняя оценка не означает автоматическое выполнение её члена; Again может вернуть цель по сроку.
3. **Решено:** один Translation = перевод примера → ключевое слово; ordinary reverse FSRS exact meaning. Самостоятельный перевод предложений на паузе: убрать из выбора новых тренировок, сохранить реализацию и историю. Переименовать видимое Word in Context в Translation. ADR-0015 уже содержал контракт контекстного reverse.
4. Предложенные уведомления: краткое подтверждение принятого действия, без постоянного верхнего баннера. Уточнить только если варианты действия требуют дополнительного экрана.
5. Визуальные варианты выбрать на богатой карточке с переводами/без. До получения измерений не требовать от владельца назначить каждый пиксель.
6. Indigo: подтвердить найденный исторический цвет на образце, если история не даёт единственного однозначного кандидата.

Не требуют повторного согласования: пользователь уже попросил первые 50 строк в фоне, сохранение готовых данных, отсутствие вспышки Preparing Training, свободный drag, оба направления идиом и отдельную Indigo. Решения о таймаутах, retry budget, cache keys и pointer implementation — ответственность инженера на основании измерений.
