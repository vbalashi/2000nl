# Управление тренировочной сессией: предложение для #250

2026-09-05. Предложение архитектуры, не реализованный код и не замена ADR 0004/0005.
Цель: одна часть приложения знает текущую карточку, принят ли ответ и что делать после ошибки.

## Что принадлежит кому

| Ответственность | Владелец |
| --- | --- |
| Какие карточки доступны, очередь, права, Known и сохранение оценки | Postgres/Platform |
| Какое задание сейчас показано, Face/Answer, pending action, следующий переход | Один Training session owner |
| Шрифты, раскладка, общий header/dock и вид состояний | Модули карточки, использующие visual contract |
| Маршрут и видимое направление приложения | Application shell |
| Отправка report и его собственный результат | Report module; принимает snapshot текущего контекста |
| Кэш/аудио/перевод | Специализированные операции; не определяют факт сохранения оценки |

Application shell передаёт данные выбранной сессии и пользовательские намерения.
Он перестаёт самостоятельно собирать внутренние chrome/footer/notice и хранить дублирующий набор флагов.
Внутреннее разбиение определяется ответственностью, а не принципом «вынести каждые 50 строк».

## Таблица переходов

| Сейчас | Событие | Следующее состояние | Что видно / что допустимо |
| --- | --- | --- | --- |
| Setup | Явный Start | Loading | Зафиксированы фильтры/размер/идентичность сессии |
| Loading | Получена валидная карточка | Face | Показана ровно текущая карточка |
| Loading | Нет кандидатов | Empty | Это не ошибка сети и не завершение уже пройденной сессии |
| Loading | Ошибка | Load failed | Retry повторяет чтение |
| Face | Show answer | Answer | Та же карточка; новый review не создаётся |
| Face/Answer | Mark known | Saving | Точная пара meaning + card type; Undo по активной mark revision |
| Answer | Learn/Grade | Saving | Одно намерение, один event id; двойной клик не создаёт второе |
| Saving | Явно отклонённое действие | Action failed | Карточка возвращена; ошибка видима |
| Saving | Ответ потерян/исход неизвестен | Reconciling | Проверка того же event; новый id не создаётся |
| Saving/Reconciling | Действие принято | Accepted / next loading | Повторное оценивание запрещено; состояние чтения независимо |
| Accepted / next loading | Следующая карточка получена | Face(next) | Переход зафиксирован после реального показа |
| Accepted / next loading | Ошибка чтения | Accepted / next failed | Текущая карточка остаётся видимой; Retry только загрузки |
| Accepted / next loading | Условие завершения выполнено | Complete | Только по принятому правилу #248 |
| Accepted / next failed | Retry | Accepted / next loading | Сохранённая оценка не отправляется заново |
| Ready | Details/History/Settings | Скрытая та же сессия | Возврат сохраняет side/hint/current target |
| Saving/Reconciling | Попытка смены направления | То же состояние | Навигация недоступна по ADR 0005 |
| Любое | Ответ от старой сессии/карточки | Без изменения | Проверяются generation/card/event identity |
| Ready | Новый Setup draft | То же состояние | Просмотр/редактирование draft не применяет фильтры |
| Ready | Явное Apply/Start новой сессии | Loading(new generation) | Старые результаты не могут заменить новую карточку |
| Любое | Refresh/logout | Конец transient UI session | Только подтверждённо принятые сервером данные гарантированно сохранены; неизвестный исход нельзя автоматически отправлять новым событием |

Hint, translation и audio — локальные состояния представления, а не альтернативные значения общей переменной loading.
Строки Details/History/Settings описывают целевую навигацию, а не уже проверенное покрытие всех маршрутов.
ADR 0005 задаёт сохранение сессии при навигации; его первая реализационная часть ограничена Training↔Library.
Остальные входы требуют отдельных проверок до расширения реализации.
При refresh во время запроса результат может остаться неизвестным: сохранение transient UI и восстановление такого запроса
между перезагрузками не обещаются текущим контрактом. Нельзя выдавать отсутствие ответа за отклонение оценки.
Notice связывается с породившей его операцией/карточкой. Нельзя переносить сообщение на две следующие карточки случайно.
Undo может иметь специально согласованную более долгую жизнь; это явное правило, а не один timer для всех уведомлений.

## Поэтапная реализация без двух конкурирующих владельцев

1. Зафиксировать тестами принятые переходы реального TrainingScreen/Platform пути.
2. Передать новому владельцу прямой/reverse turn целиком: действия, идентичность, next-load и ошибки.
3. Подключить существующее представление через небольшой interface: снимок состояния и намерения пользователя.
4. Удалить заменённые refs/effects/handlers из TrainingScreen в том же изменении.
5. Только после утверждения соответствующих строк #249/D1–D3 задача #251 заменяет визуальную компоновку на gallery; #252 подключает Details.
6. #142 переводит listening и удаляет остаточный старый путь.

Числа размера/счётчиков нельзя менять под видом рефакторинга. Сначала #248.
Нельзя заранее показывать следующую карточку так, чтобы принятая оценка и успешное чтение стали одним неразличимым исходом.
Хранение точной сессии после refresh/между устройствами требует отдельного решения и не входит в текущий этап.

## Открытые продуктовые решения для #248

S1. Лимит 10 — десять уникальных card targets или десять показов с повторениями? Рекомендация для обсуждения: десять targets, повторения показывать отдельно.
S2. «Все на сегодня» — только due/learning + дневной new budget? Рекомендация: optional practice не добавляется молча, «все подходящие» — отдельный выбор.
S3. Как завершать при Again/Hard: закончить выбранный набор или дождаться повторного предъявления? Нужны примеры до изменения scheduler.

Root готовит примеры и утверждённый контракт; агент получает таблицу переходов, а не право придумать ответы.
